# 阶段一交互、方向形成与确认协议

阶段一的目标是以尽可能少但信息量高的交互，把用户的模糊研究意图转化为一个由用户确认、具有创新性依据、初步可行、可以证伪且边界明确的唯一研究方向；方向确认后，再完成进入实验所需的研究设计。机器状态仍按 `INTAKE → DIVERGE → SEARCH → COMPARE → DRAFT → CONFIRM → GATE_CHECK` 推进。

## 基本原则

1. 交互服务于降低方向决策的不确定性，不服务于机械填写模板。
2. Codex 负责提问、完善方向、检查替代视角、执行必要侦察、比较和推荐；用户提供动机、领域判断、硬边界并确认最终方向。
3. 候选是按需使用的决策工具。不得为了数量制造虚假方向；没有实质分叉时允许一个方向进入验证。
4. High 方向专用窗口不写项目文件；方法交流保留在对话中，切换 Medium 后只在内容有实质变化时一次性保存紧凑交接，完整合同、证据和门禁只在后续检查点同步。
5. 纯讨论只完善方向；数据版本、指标、API/GPU、依赖和授权在真实设计或动作需要时处理。只有即将发生付费、外发、受限访问、依赖变更或其他高风险动作时，才请求最小必要授权。
6. 状态推进以持久化检查点和明确确认作为依据，不以轮数、候选数量或删除 `TODO` 作为依据。

## 状态与回退

```text
INTAKE → DIVERGE → SEARCH → COMPARE → DRAFT → CONFIRM → GATE_CHECK
```

- `INTAKE`：接收研究种子、动机和硬边界。
- `DIVERGE`：完善工作方向，检查实质替代视角，必要时形成非正式 IDEA，并用轻量侦察修订方向。
- `SEARCH`：只对正式入围方向开展深入创新性、可行性和反证验证。
- `COMPARE`：Codex 给出同口径比较和推荐；存在多个方向时由用户取舍，不存在真实分叉时完成单方向压力测试。
- `DRAFT`：唯一方向确认后，形成数据、baseline、指标、成功标准和实验设计。
- `CONFIRM`：确认方向与研究设计；只确认实际计划触发的权限。
- `GATE_CHECK`：检查研究设计和必要授权是否足以安全进入阶段二。

前提变化时回到最早受影响状态；回退新增转换记录，不修改历史。

## 活动方向获取

方向形成阶段只维护六项信息：

1. 用户研究意图；
2. 研究对象；
3. 核心问题；
4. 创新性假设；
5. 最小可证伪路径；
6. 范围边界。

Codex 根据“哪个未知最可能改变方向选择”决定下一步：价值偏好和领域事实询问用户；相似工作、公开数据路径和方法可行性由 Codex 侦察。一个核心问题可以附带少量紧密相关的探针，避免无意义的往返。

### High 方向专用窗口

最初 1–3 轮使用 GPT-5.6 Sol / High，只处理会直接影响研究方向准确性的工作：高信息量提问、核心问题界定、实质替代方向、创新性假设、最小可证伪路径、范围与主要风险，以及可能改变 IDEA 去留的最小标题/摘要侦察。方向基本明确后，可以向用户展示方法级草案、可行技术路线和关键取舍，以检验方向是否符合预期；这些内容保持临时，不创建正式数据、指标、实验或资源对象。首次进入时最多读取 `RESEARCH.md` 中理解当前起点所需的工作流和活动字段；同一窗口不重复读取稳定文件。

High 窗口内不得修改仓库、推进机器状态、分配稳定 ID、创建 TODO 或计划、执行正式检索与证据登记、补齐正式数据/指标/实验/资源方案、处理授权、运行验证器或测试、编写代码，或承担其他实现和维护工作。临时认识和方法讨论只保留在当前对话中；轻量侦察不能直接成为合同证据。

方向明确或用户暂停时，High 只输出一次紧凑交接：当前工作方向、研究对象、核心问题、创新性假设、最小可证伪路径、替代方向结论、方法级草案（如已讨论）、范围边界、主要风险、剩余未知和方向已明确的理由，然后停止。切换 GPT-5.6 Sol / Medium 后，由 Medium 仅在内容有实质变化时一次性写入活动区和一条合并交互记录，必要时晋升正式 `DIR`，并重新核验任何需要进入合同的侦察结果。客户端不能自动切换时，由用户切换模型或新开 Medium 会话。

用户起点不同，处理方式不同：

- 模糊想法：主动发散多个非正式 IDEA。
- 初步方向：优先完善，并检查是否存在实质替代视角。
- 明确方向：执行创新性、可证伪性和可行性压力测试，不强制制造第二方向。

## DIVERGE 内部循环

```text
理解用户信号
→ 更新当前工作方向
→ 检查替代视角
→ 必要时形成非正式 IDEA
→ 轻量创新性/可行性侦察
→ 修订、合并或淘汰
↺ 直到方向具备正式验证价值
```

Medium 接收交接后只在方向、边界、关键未知或方法取舍发生实质变化时记录一行合并日志：High 轮次范围、问题焦点、用户信号、方向变化、关键未知和下一步。纯讨论、措辞调整和未改变决策的方法备选不写文件，也不逐轮重写完整候选比较、研究合同或会话交接。正式方向、未决问题、研究对象、证据、决策、授权和切换记录在真实对象出现前保持空表。

非正式 IDEA 不分配 `DIR`、不要求完整搜索覆盖。只有满足以下条件时才升级为正式入围方向：

- 与用户动机相符；
- 核心问题、机制、贡献或验证逻辑已足够明确；
- 没有已知硬性许可、隐私、访问或资源阻断；
- 存在最低可行验证路径；
- 值得承担深入搜索成本。

进入 `SEARCH` 前必须记录替代方向检查。若只有一个正式方向，应说明为什么其他视角不构成独立方向；若有多个方向，应说明它们的实质差异。

## 分层创新性与可行性检查

### 轻量侦察

轻量侦察只服务于保留、修改或淘汰 IDEA，优先使用标题、摘要、DOI、作者、年份、综述和公开元数据，检查：

- 是否存在明显相同的问题或方法；
- 是否使用不同名称描述同一问题；
- 是否存在最低数据、baseline 和验证路径；
- 是否存在明显许可、隐私、访问、资源或方法学阻断。

侦察结论不能证明创新性，也不要求八类覆盖或证据饱和。High 期间的侦察不写入仓库；Medium 若需要使用其结论，必须重新核验并按正式证据规则登记。

### 正式验证

`SEARCH` 只验证正式入围方向。每个方向按 `docs/SEARCH_PROTOCOL.md` 比较最接近工作、实质差异、反证、数据/指标和可行性。最终方向必须给出有范围限制的创新性判断，不得声称穷尽文献。

## 方向决策检查点

进入 `COMPARE` 前应具备：

- 至少一个正式 `DIR-<nnn>`；
- 每个正式方向的核心问题、创新性风险和最小验证路径；
- 正式搜索的来源、主张、反证、停止理由和未覆盖范围；
- 对真实替代方向的同口径比较，或单方向替代检查说明。

在任何方向标记为 `已选定` 前，Codex 必须向用户展示拟定方向、研究对象、核心问题、范围边界、最小可证伪路径和方法概览，并请求明确确认；沉默、继续讨论或一般性认可不视为确认。进入 `DRAFT` 前必须恰好一个方向为 `已选定`。其他正式方向应为 `已否决` 或 `已合并` 并说明理由；只有一个方向时记录压力测试和用户确认即可。

方向总结至少包含：研究对象、核心问题、机制或假设、预期贡献、与最近工作的实质差异、最小可证伪路径、基本可行性、主要风险、范围边界、选择理由和剩余未知。

## 研究设计检查点

方向确认后再形成；详细对象行只保存定义和关系，确认来源、状态、日期、决策与证据集中记录一次：

- 数据与合法访问路径；
- baseline；
- 指标与统计口径；
- 成功标准；
- 主要实验、必要消融与稳健性验证；
- 计划使用的资源类型和失败停止规则；
- `RQ → DATA → BASE → METRIC → SC → exp` 关系。

到达 `DRAFT` 时按真实对象创建以下最小表，不预留空行：`研究问题 ID｜当前值`，`贡献 ID｜当前值｜比较 baseline ID`，`成功标准 ID｜当前值｜关联研究问题 ID`，`数据 ID｜当前值｜来源、版本与许可证`，`baseline ID｜当前值｜上游版本或 revision`，`指标 ID｜当前值与统计口径｜所需数据 ID`，以及 `研究问题 ID｜数据 ID｜baseline ID｜指标 ID｜成功标准 ID｜阶段二实验 ID｜关系状态`。对象的确认元数据只写在 `RESEARCH.md` 的设计确认表和关联 `DEC`/`CLM` 中。

具体数据版本、模型、API/GPU 数据流和依赖只在真实实验计划需要时填写。未计划使用的能力默认不存在，不创建占位授权，也不要求逐项解释“不适用”。成功标准必须在正式运行前固定，允许在方向确认后根据合理的设计或预实验依据形成。

## 动作触发授权

授权只在动作即将发生前创建 `AUTH-<nnn>`：

- 新增付费操作；
- 数据或文件发送到外部服务；
- 访问受限数据、模型、数据库或资料；
- 处理个人信息、内部或保密数据；
- 增加、删除或升级依赖；
- Skill 上传数据、产生费用、保存受限内容或修改 `.agents/`；
- 生成其他授权门禁交付物。

授权必须说明动作、对象、范围和适用决策。一般性认可不能替代具体授权。没有相关计划时不创建 `AUTH` 行。

付费动作即将发生时，披露服务、用途、计划规模、价格依据、预计费用范围和异常停止条件，并取得用户确认。

## 确认与门禁

确认分为两个检查点：

1. 方向确认：Codex 先展示唯一拟定方向、核心问题、范围边界和方法概览，再由用户明确确认方向与选择理由。
2. 研究设计确认：用户确认数据、baseline、指标、成功标准和主要实验；实际触发的权限另行确认。

只有持久、实质性取舍创建 `DEC-<nnn>`，例如最终方向、正式候选否决、数据选择、核心指标、重要方法取舍和范围变化。一个明确决策可以覆盖一组紧密相关字段；措辞调整不创建决策。

`GATE_CHECK` 执行严格验证，确认唯一方向、研究设计关系、正式证据、实际需要的授权和 `experiments/TODO.md` 均一致，然后请求用户同意进入阶段二。

## 精简恢复规则

High 窗口不维护项目文件。Medium 接收交接后，仅在交接包含实质变化时一次性维护：最近轮次、当前子状态、当前工作方向、替代方向检查、关键未知和下一步。纯方法讨论、措辞调整、重复摘要和未改变决策的轮次不触发写入；没有新会话或检查点时，不重复读取稳定协议或完整合同。

新会话恢复时读取 `AGENTS.md`、`RESEARCH.md` 和当前子状态直接相关的协议章节；只有状态切换、规则冲突或门禁检查时才读取完整协议。详细搜索证据继续由 `research/` 保存，不把网页全文、工具原始响应或完整聊天写入活动上下文。
